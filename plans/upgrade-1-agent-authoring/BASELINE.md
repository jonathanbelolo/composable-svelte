# Upgrade 1 baseline: reliable application authoring

This is a bounded reconciliation for Upgrade 1. It does not close the original remediation mission or amend the canonical ledger.

## Proven and released baseline

- `@composable-svelte/core@0.13.0-next.0` is published under `next`; `latest` remains `0.12.2`. The qualified archive is SHA-256 `bf595393c8e21d6aeaf6dafa1d1b665c531f14895259d12eec131b1249d738d2`. Evidence: [`RELEASE-RESULT.json`](../core-prerelease-2026-09-21/RELEASE-RESULT.json), [`RELEASE-QUALIFICATION-FINAL.json`](../core-prerelease-2026-09-21/RELEASE-QUALIFICATION-FINAL.json).
- The release includes the managed application host and ownership surface, routing and managed presentation/view contracts, deferred dismissal, request lifetime behavior, and public single/group motion recipes. Its shipped guides include [`application-ownership.md`](../../packages/core/docs/application-ownership.md), [`application-routing.md`](../../packages/core/docs/application-routing.md), [`application-views.md`](../../packages/core/docs/application-views.md), and [`application-motion.md`](../../packages/core/docs/application-motion.md), as verified in the qualified tarball. [`application-contract.md`](../../packages/core/docs/application-contract.md) is a new local Upgrade 1 contract reviewed after `0.13.0-next.0`; it is not in that published archive and must be qualified in the next candidate before it can serve as the installed authoritative entry point.
- Actual-tarball qualification already proves useful pieces of the future authoring gate: isolated physical installation without workspace aliases or peer bypasses; public types/exports; strict Svelte checks; deterministic SSR; browser presentation and motion behavior; reduced-motion/cleanup behavior; interrupted-request behavior; extracted shipped-document examples; and a stale-dismissal mutation control. Reuse [`installed-motion-consumer-v1/final-consumer-v4`](../core-prerelease-2026-09-21/evidence/installed-motion-consumer-v1/final-consumer-v4), [`installed-core-consumer-v1/QUALIFICATION-FINAL-V4.json`](../core-prerelease-2026-09-21/evidence/installed-core-consumer-v1/QUALIFICATION-FINAL-V4.json), and [`installed-request-lifetime-v1/QUALIFICATION-FINAL-V4.json`](../core-prerelease-2026-09-21/evidence/installed-request-lifetime-v1/QUALIFICATION-FINAL-V4.json).

These facts satisfy reusable implementation prerequisites, but the ledger still records the associated specification blocks as open because it has no joined closure evidence. In particular, open ledger status alone is not evidence that the released runtime is absent.

## Genuinely remaining Upgrade 1 obligations

1. **One authoritative, packaged authoring contract.** Reconcile the shipped documents into a short entry path with explicit supported paths, ownership, limitations, and gap reporting. Preserve the current public managed and compatibility contracts; do not imply automatic presentation defaults or public custom motion drivers that this upgrade does not deliver. Relevant open obligations: `SPEC-009`–`SPEC-013`, `SPEC-170`, `SPEC-173` in [`LEDGER.json`](../framework-remediation-2026-09-18/LEDGER.json).
2. **A genuinely managed starter.** The packaged [`consumer`](../../packages/core/consumer) is qualified as a toolchain smoke example but explicitly uses `createStore`/`onDestroy`; it is not the managed starter required by `SPEC-099`/`SPEC-170`. Replace its application assembly with the managed host, routing, one optional feature, one injected business effect, and deterministic tests while retaining its check/build/SSR/browser/theme coverage. Use the installed `final-consumer-v4` application as source material, not as a claim that the starter is already complete.
3. **Bounded architecture qualification.** [`scripts/consumer-architecture`](../../scripts/consumer-architecture) already provides fail-closed TypeScript/Svelte graph traversal, alias/re-export/dynamic-import handling, externally pinned policy validation, package/version/tarball provenance, and 30 passing focused tests (re-run during this reconciliation). Its README correctly says it has no rule evaluators: `AVAILABLE_EVALUATORS` is empty and qualification mode always returns `refused`. Its policy and CLI pairing also accept only plain `x.y.z`, so they cannot currently pair with the released `0.13.0-next.0` baseline. Implement and adversarially test a named, versioned evaluator set and an explicit prerelease-compatible pairing contract; package it outside browser runtime bundles; keep policy and qualification records outside generated-project authority. Relevant open obligation: `SPEC-161` and stage 6.
4. **Installed-package fresh-agent exercises.** No preserved evidence satisfies `AAM-15`, `SPEC-192`–`SPEC-196`, or `STAGE-6`. Run two held-out generic scenarios, three independent runs each, from pinned installed packages and published entry instructions only. Each run must cover construction and a change request, record first attempts/repairs/interventions, and pass externally controlled type/Svelte checks, functional and held-out acceptance tests, production build, and the architecture checker. At most one diagnostics-guided repair is allowed; missing or disabled gates fail the run.

## Recommended reuse and evidence shape

- Start the managed starter from the small packaged consumer toolchain and transplant only the reviewed managed assembly patterns from `final-consumer-v4/src/{App.svelte,model.ts}` plus its presentation, motion, public-contract, SSR, and export tests.
- Extend the existing checker substrate rather than creating a second scanner. Preserve its analysis-only versus qualification distinction and its negative provenance controls; add semantic rule mutants for aliases, helpers, re-exports, fake registrations, unsupported constructs, and empty/missing scope.
- Reuse [`scripts/verify-consumer.mjs`](../../scripts/verify-consumer.mjs) for isolated starter/package mechanics, but create a separate orchestrator-owned fresh-agent harness and acceptance suite. Generated projects must not control package pins, checker policy, held-out tests, or gate execution.
- Freeze each candidate tarball and record archive hash, installed identity/integrity, policy/checker version, agent configuration, prompts, first-pass output, repairs, final results, and human intervention. Keep package qualification, architecture compliance, and fresh-agent reliability as separate receipts.

The prerelease checkpoint itself states that automatic animation defaults, stable companion qualification, and the broader remediation mission remain open. Those are outside this upgrade except where an honest limitation must be documented.
