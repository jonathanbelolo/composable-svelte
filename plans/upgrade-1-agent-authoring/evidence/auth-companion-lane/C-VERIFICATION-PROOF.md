# Managed email verification candidate proof

Status: independently reviewed local candidate, ready for parent integration. This extends the reviewed login/MFA, signup and password-recovery slices. The remaining auth inventory rows and publication are open.

## Behavior and ownership

`createAuthFeature()` now owns an optional email-verification slot. `openEmailVerification` and `restartEmailVerification` seed an optional address for resend; the link token remains an `EmailVerification` prop. The component starts one verification exchange on client mount, while the same genuine view can dispatch `verificationRequested` headlessly. SSR rendering starts no work. Verify and resend use separate cancellable effect IDs under the same temporary owner. A headless test proves one can fail while the other remains pending; replacement cancels both and drops late results. A nested two-sibling test starts both operations in both auth instances, removes one owner, and confirms the other instance remains live despite the shared fixed IDs.

A verification result that issues a session goes through the feature's shared accepted/refused handoff with source `emailVerification` and retires the flow. A verified result without a session stays visible and establishes no session. A parent reads it only after the matching routed `verificationSucceeded` action. Each `resendSucceeded` can likewise be observed after its matching routed action, including a repeated resend. The managed form's sign-in control dispatches `signInRequested` through the owned view and presents a fresh login. The feature stores no app route.

`EmailVerification` in managed mode accepts `PresentationView<EmailVerificationState, EmailVerificationAction>`, excludes the standalone session store and callbacks, and renders nothing when the owner retires. Its visible content is keyed by its view and resend/sign-in click handlers capture that view; a still-attached button click before a pending swap reaches the old sibling, then the new button reaches the new sibling after the swap. A same-token restart through `FeatureOutlet` exchanges exactly once for each new managed owner; a separate kept-mounted component view swap exercises the token guard's owner reset. A kept-mounted retired view renders nothing and starts no replacement request. Standalone mode retains one component-lifetime token guard and stable DOM when a consumer recreates its `flowStore` wrapper; the bounded failure regression exercises failed-token feedback, button identity and focus. A second regression switches to a distinct standalone store and proves a click reaches the latest store without a second token exchange. Standalone props and component handoff remain available. Compile-only real Svelte `ComponentProps` checks reject illegal managed props, spread-injected session stores, plain stores substituted for views, and a retired view substituted for a standalone store.
