## Historical baseline findings (retained audit trail)

The following notes describe the inherited baseline and early review sequence, not the current candidate disposition. The current matrix and B–K proof records above supersede their managed-acceptance and README-status statements.

The baseline component scan found `LoginForm` asks for a non-optional `LoginState`, `dispatch` and `subscribe`; `ChildView.state` is `LoginState | undefined`. Other flow forms similarly require live state. `AuthGuard` and `RoleGate` only ask for session state. Many forms receive `sessionStore.dispatch` plus business callbacks; those remain standalone compatibility surfaces, while managed assembly needs a parent reducer result route. `packages/auth/README.md` currently uses `history.pushState` in its login quickstart and has no `defineApplication` / `defineViews` / `FeatureViews` recipe.

Independent Opus review 2 found a current production defect in seven form-backed rows: signup, forgot/reset password, change email/password, magic-link request and MFA enrolment still start the dependency request for a `submissionSucceeded` action the form reducer refused. A stamped idle action was reproduced for each. Their existing standalone test IDs above do not close this case. See `OPUS-REVIEW-2.md` for exact source locations and review evidence.

**Disposition (standalone source fix landed, independent re-review pending).** The seven reducers now start a request only when `completesSubmissionInFlight(before, after, action)` holds. That is an internal, unexported helper in `flows/submission-feedback.ts`, and it applies the same two checks login and MFA challenge make inline: the form reducer changed its state (so it did not refuse a stale stamped result), and the form was submitting beforehand (so an unstamped result while idle does not count). Flow-specific rules:

| Flow | Rule added on top of the shared check | Behaviour that stays the same |
| --- | --- | --- |
| Signup, forgot password, magic-link request, change email, change password | None; a stale result no longer sends whatever the fields hold now. For change email and change password, that includes the empty fields a success leaves. | A new submission cancels and replaces the request in flight (fixed ID). Resubmitting after a success or after `sent` is still allowed. |
| Reset password | The check runs before the missing-token refusal, so a stale result neither spends the token nor sets `token_expired`. | An accepted result with no token still reports `token_expired` and makes no request. |
| MFA enrolment | Also requires `confirming` or `submitting`. After `enrolled`, a second confirmation would fail, return the flow to `confirming` and hide the once-only recovery codes. | A second code during `submitting` still replaces the first. The existing `enrolmentId === null` refusal stays. |

Evidence is `tests/submission-feedback.test.ts`: 38 tests, a 5-test contract run for each of the seven flows plus 3 flow-specific tests. The contract covers:
- a stamped result while idle makes no request;
- a genuine submission makes exactly one request with the valid fields;
- replaying that genuine stamped result makes no second request;
- a superseded `submissionId` is refused and the current one accepted;
- the pre-reset and post-reset `submissionId` after `formReset` are refused, and the next submission is accepted;
- an unstamped result while idle is accepted by the form but refused by the flow, while one that completes a submission is accepted;
- a second genuine submission aborts the first request's signal and still settles.

Measured: before the fix, 31 of those tests failed and each failure was the defect, a request or `submitting` status. After the fix, 239/239 passed across that file and the flows' existing flow and component files. Mutations, each restored byte-identical by checksum:
- each flow's guard reverted to `action.action.type !== 'submissionSucceeded'` fails 4 of that flow's contract tests, and 5 for reset password, which adds the missing-token test. The supersession control keeps passing, as intended.
- removing enrolment's phase rule fails both enrolment phase tests.
- removing the helper's identity check fails the superseded-ID test in all 7 flows.
- removing its `isSubmitting` check fails the unstamped-idle test in all 7 flows.

Still open:
- Change email and change password rebuild the form with `createInitialFormState` on success, which restarts `submissionId`. A stamped result carrying an old lifetime's ID could match a later submission with the same number. No reachable path is known because core's `submit-form` effect has already completed, but a monotonic counter across that reset would close it. That is not done here.
- Reset password still allows a resubmission after `reset`. This task did not change that.
- Managed acceptance for these rows (owner retirement, `ComponentProps`, installed recipe, SSR) remains open as listed above.
- Independent Opus re-review of this fix has not been run.

## T2 auth proof and composite ADR inputs

Use persistent `SessionState` in the parent and temporary managed login/MFA slots. Core currently reduces a child action before the parent (`packages/core/src/lib/navigation/managed-integration.ts`, `ManagedComposition.reduce`), so the parent can consume a lifted success/MFA business action, call `sessionReducer` and choose the app route in one turn. It must check that the child accepted the action: manually authored stale domain feedback is distinct from owner-stamped effect feedback. Retiring a flow must suppress its pending effect and any child effect produced on its retiring action, while parent follow-up effects retain parent ownership. The B proof must test those distinctions before an ADR accepts this as the shared composite contract. The same ADR should allow chat to expose a leaf conversation with optional code/media presentation children omitted without declaration imports of absent peers.
