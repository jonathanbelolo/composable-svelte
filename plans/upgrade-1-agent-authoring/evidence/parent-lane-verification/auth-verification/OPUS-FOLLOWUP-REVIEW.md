**Verdict: clear to land. There are no blocking defects in the source.** Two of the tests prove less than the evidence file says they do, and I'd tighten those before recording this as closed. I read the code only and ran no tests; the verdict is also saved in `/Users/jonathanbelolo/.claude/plans/read-only-independent-opus-5-5-quirky-beaver.md`.

**Confirmed from the source:**
- **M1 is fixed.** In standalone mode the component uses one fixed key for its whole life (`EmailVerification.svelte:109-111`). A rebuilt wrapper therefore doesn't remount the DOM (line 169) or reset the once-only token guard (line 116). Actions are sent to whatever `flowStore` is current at click time (line 111).
- **Managed mode: one exchange per owner.** Core returns the same view object for as long as an owner lives (`managed-integration.ts:415-420`), so the key only changes when the owner is replaced. A failed token is not exchanged again under the same owner. The resend and sign-in handlers each keep the view their subtree was rendered for (lines 195 and 252).
- **Retired and SSR are safe.** A retired view has no state, so the exchange effect returns early and the `{#if flow}` block renders nothing. The session handoff effect does nothing in managed mode, and no effect runs during SSR.
- **L1 is fixed.** The CHANGELOG now says `EmailVerificationAction` gains `signInRequested` and that exhaustive switches need the new case.

**Lesser findings:**
1. **The "departed button" check in `managed-forms.test.ts:333-337` always passes.** By the time the old button is clicked, it has already been removed from the page. Svelte 5 handles `click` with a single listener at the root, and a click on a removed element never reaches it. So `resends === 0` would hold even if the handlers didn't keep their own view. The only thing the test proves is that the subtree remounts, so the evidence sentence about a departed button overstates it. Fix: click the old button before `flushSync`, while it is still on the page, and assert that the resend goes to store `one`.
2. **The L2 test doesn't check the component's reset line.** `FeatureOutlet` mounts a fresh component for each owner, so the restart test at `managed-forms.test.ts:405-411` passes even if line 116's `requested = null` is deleted. It covers the full recipe, which is what L2 asked for. It does not cover a component that stays mounted across a restart with the same token; the existing swap test passes `token={null}`.
3. **The M1 test hangs instead of failing when the fix is broken.** At `email-verification.test.ts:392-394`, `verifyEmail` rejects on every call. With the fix broken, fail-and-retry becomes an endless loop that blocks the test's own timers. That matches the mutation run that hung. Fix: reject on the first call, then return a promise that never settles, so a regression fails cleanly with a call count of 2.
4. **No test shows standalone dispatch reaching a newer store.** All the rebuilt wrappers in the M1 test send to the same store, so an outdated wrapper would pass too. The source (line 111) is correct.
5. **The CHANGELOG doesn't name the new handoff source.** `AuthHandoffSource` gains `'emailVerification'` (`feature.ts:83`), which will break a consumer that switches exhaustively on `handoff.source`, and the entry doesn't name it (the reset entry does name `resetPassword`). `CHANGELOG.md:18` still says the handoff is set only for "login, MFA or signup".
6. **No test keeps the component mounted while its view retires.** The source handles this correctly.
