# Independent T6 registry review

**No blockers.** The change is fail-closed, `starter` is the only selectable bundled policy, and its bytes and behaviour are unchanged. No code, media, chat or combined profile is registered, shipped or selectable; the README and T6-REGISTRY.md both describe them as future intent only.

**What I verified**
- **Starter bytes and behaviour:** `policies/starter.json` has no changes against HEAD. Its SHA-256 is `389430147e64…d8b3`, which matches `BUNDLED_STARTER_SHA256`. `loadBundledPolicy('starter')` reads the same file through an absolute path, and a test checks it gives exactly the same result as `loadBundledStarterPolicy()`.
- **Selector handling (`check.mjs:59-61`):** any value starting with `bundled:` is treated as a registry name, so it can never fall back to a file path. The name must be a plain lowercase slug (`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`), which rules out empty names, `/`, `\`, `..`, NUL, case variants and whitespace. The lookup accepts only entries owned by the registry itself, not inherited ones. With `__proto__`, `constructor` or `toString` as the name, the slug accepts it but the own-entry check refuses it, because the registry has no prototype. An unknown name exits with a usage error before any file is read. The CLI test puts real `bundled:evil.json` and `bundled:/starter` files in the working directory and confirms neither is loaded.
- **Pin flag and qualification:** `--policy-sha256` together with a bundled policy is still a usage error (line 62). Qualification with a bundled policy is still refused (line 76), and `isQualificationPass` still requires `source === 'external'` (line 332). None of these lines changed.
- **Hash before parse:** `validateBundledPolicyBytes` checks that the pin is well-formed, then hashes the bytes, compares, and only then decodes, parses and validates. The tamper test appends non-JSON bytes and gets `policy-pin-mismatch` rather than `policy-parse-error`, so it really does show the hash is checked first.
- **Registry immutability:** the registry has no prototype and is frozen, and so is each entry. Its keys are exactly `['starter']`, and a test confirms that trying to modify it throws.
- **External policies:** the `loadPolicy` path is unchanged, including the lowercase-hex pin rule. A byte-identical copy of the starter supplied as an external file is reported as `source: 'external'`, never promoted to bundled.
- **No new permissions or weaker checks:** the diff adds no capability grants, detectors or wildcard approvals, and doesn't touch `validatePolicy` or the opaque-package identity and provenance rules.
- **Package archive:** `package.json` `files` includes `policies/`, and `test/inspect-archive.mjs` requires `policies/starter.json` byte-for-byte.
- **Tests:** I ran `node --test src/bundled-policy.test.mjs src/check.test.mjs` and all 12 passed; the worktree was unchanged afterwards. The T6 note says this command wasn't permitted in its session, but it worked here. I did not re-run the full 525-test suite, `test:installed` or `check:archive`, because the last two need a pack step, which would modify files.

**Findings (all non-blocking, low severity)**
1. **An entry can pass validation and then change** (`bundled-policy.mjs:34-36` and `78-84`). The code checks that entries are frozen, but a frozen object can still use getters. `getBundledPolicyEntry` validates `entry.path` and `entry.sha256`, then `loadBundledPolicy` reads both again, so a getter could return different values the second time. Example: a frozen entry with `get path()` that returns a different file on its second read. This is only reachable through the test-only `registry` option, not the CLI, because the production entry holds plain values. Fix: copy the values into local constants once, or require plain data properties via `Object.getOwnPropertyDescriptor`.
2. **Entry paths aren't tied to the shipped `policies/` folder** (`bundled-policy.mjs:14-16`). An entry only needs an absolute path, and `inspect-archive.mjs` hard-codes `policies/starter.json` rather than walking the registry. That's fine with only the starter. But a future entry could point somewhere outside `policies/` and still pass, with the archive check only catching it by accident. Before registering any companion profile, add a test that every production entry resolves inside `policies/` and appears in the archive's expected file list. This fits under gate 3 in T6-REGISTRY.md.
3. **The pinned archive policy is checked only indirectly.** `inspect-archive.mjs` checks that the archived policy bytes match the source file, and a unit test checks that the source file matches the pin. So the archived bytes match the pin, but nothing asserts it directly. It would be worth asserting `hash(archive policies/starter.json) === BUNDLED_STARTER_SHA256` when gate 3 lands.
4. **The output doesn't record which bundled policy was chosen.** With a single entry, the policy id plus its SHA-256 identifies it, and T6-REGISTRY.md already lists this as open decision 4. It needs deciding before a second entry exists.
